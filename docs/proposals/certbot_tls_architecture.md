## 1. Executive Summary & Problem Statement

### 1.1 Executive Summary

PacketTracerWeb operates a multi-container educational virtualization stack consisting of `pt-nginx1` (custom Nginx `1.27.0` edge gateway), `pt-management` (Flask/Gunicorn admin and student portal backend), `pt-guacamole` + `pt-guacd` + `guacamole-mariadb` (Apache Guacamole remote desktop gateway), and `ptvnc1..N` (containerized Cisco Packet Tracer desktop instances). Today, external HTTPS termination on ports `443` and `5000` relies exclusively on either a self-signed certificate generated by `generate-ssl-cert.sh` or manually uploaded files that fail due to read-only single-file bind mounts.

This specification defines a production-ready, zero-downtime **Automated Certbot (Let's Encrypt) TLS Integration** for PacketTracerWeb on branch `expirement`. The architecture achieves:

1. **Automated ACME HTTP-01 Issuance & Domain Routing**: Carves `location ^~ /.well-known/acme-challenge/` out of port `80` in `ptweb-vnc/pt-nginx/generate-nginx-conf.sh` before the `301` HTTPS redirect and free of GeoIP `444` drops and `limit_req` throttling, while replacing hardcoded `server_name localhost;` with validated `SERVER_NAME` / `CERTBOT_DOMAIN` / `CERTBOT_EXTRA_DOMAINS` resolution.
2. **Unified TLS Coverage & Zero-Crash Bootstrap**: Covers both port `443` (Guacamole + student portal) and port `5000` (`pt-management`) under the active certificate, enforces `[PROP-C3-03]` Mozilla Intermediate ECDSA+RSA AEAD ciphers with conditional HSTS, and guarantees `pt-nginx1` boots cleanly on `:80/:443/:5000` before first ACME issuance via non-interactive self-signed bootstrap fallback.
3. **Autonomous 12-Hour Renewal & Zero-Downtime Reload**: Introduces a dedicated `pt-certbot` service (without mounting `/var/run/docker.sock`), replaces single-file `:ro` SSL bind mounts with directory mounts (`./ssl`, `./certbot/conf`, `./certbot/www`), and implements a dual reload path (a read-only `readlink -f` SHA-256 content-hash watcher in `pt-nginx1` plus synchronous `nginx -t && nginx -s reload` from `pt-management`) that rotates certificates without terminating active Guacamole WebSocket sessions.
4. **Full `pt-management` Admin Portal Integration & Coexistence**: Fixes `EnvConfigManager._update_env_content()` to append missing keys in-place without breaking the `/app/.env` bind-mount inode, adds `CertbotManager` and `/api/certbot/*` endpoints with `fcntl.flock` concurrency control across Gunicorn workers, fixes `FileUploadManager` to write/validate X.509 certificate/key pairs into RW `/project/ssl/`, and extends `templates/env_settings.html` + `static/js/env-config.js` with a cohesive `TLS_MODE` (`self-signed` | `manual` | `certbot`) management experience.
5. **Deployment & Security Reconciliation**: Aligns `ptweb-vnc/docker-compose.yml`, `deploy.sh`, `deploy-full.sh`, and `remove-instance.sh`, hardens private key permissions (`0600`), excludes `/certbot/` in `.gitignore`, and preserves all `health_check.sh` and `tests/test_tier0_local.sh` invariants.

### 1.2 Current Architectural Gaps

An empirical audit of branch `expirement` reveals seven interlocking deficiencies preventing automated Let's Encrypt TLS today:

1. **Port 80 Server-Level `return 301` Blocks ACME HTTP-01 (`ptweb-vnc/pt-nginx/generate-nginx-conf.sh:395-399`, `ptweb-vnc/pt-nginx/conf/ptweb.conf:8-12`)**:  
   When `ENABLE_HTTPS=true`, the port `80` `server` block places `return 301 https://$host$request_uri;` directly at server scope. Because Nginx evaluates server-level `return` directives during `NGX_HTTP_SERVER_REWRITE_PHASE` *before* `location` matching (`NGX_HTTP_FIND_CONFIG_PHASE`), any request to `/.well-known/acme-challenge/<token>` is immediately redirected to HTTPS unless the redirect is moved inside `location /` after an explicit ACME challenge location.
2. **Hardcoded `server_name localhost;` (`generate-nginx-conf.sh:397,405,420,447,487`)**:  
   All port `80`, `443`, and `5000` `server` blocks hardcode `server_name localhost;`, ignoring production FQDNs required for ACME issuance and virtual-host clarity.
3. **GeoIP `444` Drops and Rate Limiting (`generate-nginx-conf.sh:219-253`, `nginx.conf:38-55`)**:  
   `render_geoip_check()` drops non-whitelisted or blocked countries with `return 444`, and `render_rate_limit_directive()` applies `limit_req zone=pt_req_zone`. Let's Encrypt validation servers connect from arbitrary global IPs and must bypass both controls on `/.well-known/acme-challenge/`, while keeping `health_check.sh` lines `391`, `496`, `501`, and `524` assertions on `location /` intact.
4. **Single-File `:ro` SSL Bind Mounts Cause Stale Inodes & `EROFS` (`deploy.sh:328-333`, `deploy-full.sh:102-107`, `remove-instance.sh:200-205`, `ptweb-vnc/docker-compose.yml:56-57,80-81`)**:  
   Host `./ssl/server.crt` and `./ssl/server.key` are bind-mounted individually into both `pt-nginx1` and `pt-management` as `:ro` files.
   - In `pt-nginx1`, atomic file replacement or Certbot `live/<domain>/*.pem` symlink rotation leaves the container bound to the original inode across `nginx -s reload`.
   - In `pt-management`, `FileUploadManager` (`pt-management/ptmanagement/api/file_upload.py:26-27,37,193,265,283,346`) writes to `/etc/ssl/certs/server.crt` and `/etc/ssl/private/server.key`, failing with `OSError: [Errno 30] Read-only file system` (`EROFS`), rejects `.pem` keys (`file_upload.py:19` vs `env_settings.html:636`), uses unsafe `startswith()` backup path checks, performs no X.509/key-pair validation, and never reloads `pt-nginx1` (nor does `POST /api/upload/restore` at `upload_routes.py:180`).
5. **`EnvConfigManager._update_env_content()` Silently Drops New Keys & Bash `source` Risks (`pt-management/ptmanagement/api/env_config.py:78-80,473-521`, `generate-nginx-conf.sh:17`)**:  
   `_update_env_content()` iterates over existing `.env` lines and only rewrites keys matching `rf'^{env_var}='` (`lines 502-503`), silently dropping new keys (`TLS_MODE`, `SERVER_NAME`, `CERTBOT_*`). Moreover, `read_env_file()` (`lines 78-80`) does not strip surrounding quotes, while `generate-nginx-conf.sh:17`, `deploy.sh:16`, `deploy-full.sh:14`, `remove-instance.sh:16`, `add-instance.sh:19`, and `health_check.sh:28` execute `source` on `.env`—meaning unquoted space-separated `SERVER_NAME` values crash bash with `exit 127: command not found` or execute tokens matching binaries.
6. **Missing `pt-certbot` Service and Missing `pt-nginx1` Reload Watcher (`ptweb-vnc/pt-nginx/Dockerfile:74`)**:  
   No ACME client container exists, and `pt-nginx1` executes `CMD ["nginx", "-g", "daemon off;"]` directly with no background certificate/config watcher to trigger `nginx -t && nginx -s reload` after unattended renewals.
7. **`docker-compose.yml` vs `deploy.sh`/`deploy-full.sh` Divergence & Conditional Port `443` (`ptweb-vnc/docker-compose.yml:1,41-91`, `deploy.sh:359`)**:  
   `ptweb-vnc/docker-compose.yml` uses stock `image: nginx:latest` (lacking GeoIP), maps `"8080:80"` (breaking HTTP-01 on port `80`), omits port `5000` on `pt-nginx1`, binds host `"5000:5000"` directly to `pt-management` (conflicting with `pt-nginx1:5000`), sets `ENABLE_HTTPS: 'true'` instead of `STANDALONE_SSL` (`pt-management/entrypoint.sh:36`), and sets `SHARED_HOST_PATH: ./shared` (which causes Docker Engine `HostConfig.Binds` HTTP `400` errors in `container.py:377-380` unless an absolute host path is supplied). Additionally, `deploy.sh:134` skips rebuilding `pt-nginx` if `pt-nginx:latest` already exists, `deploy.sh:359` conditionally omits `-p 443:443` when `ENABLE_HTTPS=false` (blocking runtime HTTPS enablement without container recreation), and `remove-instance.sh:198-216` recreates `pt-nginx1` without `--network ptnet`, `-p 5000:5000`, unconditional `-p 443:443`, or `nginx.conf` mount.

## 2. ACME Challenge Flow(s)

### 2.1 Primary Flow: HTTP-01 Webroot Challenge via `pt-nginx1` Port 80

HTTP-01 is selected as the primary ACME challenge mechanism because `pt-nginx1` already exposes TCP port `80` publicly and requires no external DNS provider API credentials.

#### Step-by-Step HTTP-01 Sequence
1. **Preflight & Trigger**: Either `pt-management` (on admin action via `docker exec pt-certbot certbot certonly ...`) or `pt-certbot`'s 12-hour `certbot renew` loop initiates an ACME order against Let's Encrypt (staging or production directory).
2. **Token Placement**: `pt-certbot` writes the challenge token file into `/var/www/certbot/.well-known/acme-challenge/<token>` (backed by host `./certbot/www/`).
3. **CA Validation Request**: Let's Encrypt validation servers resolve `CERTBOT_DOMAIN` (and any `CERTBOT_EXTRA_DOMAINS`) and issue `GET http://<domain>/.well-known/acme-challenge/<token>` to `pt-nginx1:80`.
4. **Nginx Location Match**: `pt-nginx1` matches `location ^~ /.well-known/acme-challenge/` inside the port `80` `server` block (reads from `:ro` mount `/var/www/certbot`, serves `default_type "text/plain"` with `try_files $uri =404`).
5. **Certificate Finalization**: Upon HTTP `200` verification, Let's Encrypt signs the leaf + intermediate chain; `pt-certbot` writes versioned files into `/etc/letsencrypt/archive/<domain>/` and updates symlinks in `/etc/letsencrypt/live/<domain>/{fullchain,privkey}.pem`.

#### Why `return 301` Must Move Inside `location /` and Use `location ^~`
In `ptweb-vnc/pt-nginx/generate-nginx-conf.sh:395-399`, the port `80` block is currently:
```nginx
server {
  listen 80;
  server_name localhost;
  return 301 https://$host$request_uri;
}
```
In Nginx request processing:
- A `return` placed directly inside `server { ... }` executes in **`NGX_HTTP_SERVER_REWRITE_PHASE`**, which runs *before* `NGX_HTTP_FIND_CONFIG_PHASE` (location selection). Simply adding a `location /.well-known/acme-challenge/` block alongside a server-level `return 301` will **never** reach that location block.
- Moving `return 301` into `location / { return 301 https://$host$request_uri; }` defers redirection until after longest-prefix matching (`^~`).
- Using the **`^~` prefix modifier** (`location ^~ /.well-known/acme-challenge/`) accomplishes three requirements simultaneously:
  1. Prevents regex locations (such as `location ~ /\.ht { deny all; }` or future regex rules) from overriding ACME challenge paths.
  2. Leaves the ACME block completely outside `render_common_server_block()` (`generate-nginx-conf.sh:255-369`), guaranteeing zero GeoIP `return 444` checks and zero `limit_req` throttling for global Let's Encrypt validators.
  3. **Preserves `health_check.sh` grep invariants**: `health_check.sh:391,496,501` run `grep -A 30 'location /'` and `grep -A 5 'location /'` on `/etc/nginx/conf.d/ptweb.conf`. Because `location ^~ /.well-known/acme-challenge/` starts with `location ^~`, it does not match `'location /'`, whereas `location /` on port `443` retains `render_geoip_check` and `render_rate_limit_directive` verbatim (`health_check.sh:524` `proxy_pass` also remains intact). Note: on port `80` when `ENABLE_HTTPS=true`, `location / { return 301 ... }` also matches `'location /'`, and `grep -A 5 'location /'` across `ptweb.conf` succeeds as long as port `443`'s `location /` block contains the GeoIP/rate-limit lines (`grep -q` exits 0 if any matching block satisfies the assertion).

#### Port 80 & Port 443 Generated Blocks
When `ENABLE_HTTPS=true`:
```nginx
# HTTP -> HTTPS redirect with ACME HTTP-01 carve-out
server {
  listen 80;
  server_name ${EFFECTIVE_SERVER_NAME};

  location ^~ /.well-known/acme-challenge/ {
    root ${CERTBOT_WEBROOT};
    default_type "text/plain";
    try_files $uri =404;
  }

  location / {
    return 301 https://$host$request_uri;
  }
}
```
When `ENABLE_HTTPS=false` (e.g., initial HTTP-only provisioning before enabling HTTPS), the identical `location ^~ /.well-known/acme-challenge/` block is emitted at the top of the port `80` `server` block (`generate-nginx-conf.sh:418-426`) immediately before `render_common_server_block`. Additionally, the same `location ^~ /.well-known/acme-challenge/` block is emitted at the top of the port `443` `server` block before `render_common_server_block` so that if an external load balancer or redirect ever forwards an ACME challenge to `:443`, it still resolves cleanly without GeoIP or rate-limit interference.

### 2.2 Domain `server_name` Resolution, Safe `.env` Parsing & Hostname Validation

`generate-nginx-conf.sh` must **not** execute `source "$ENV_FILE"` (`line 17`). Instead, it uses a safe line-by-line key-value parser (`while IFS= read -r` splitting on the first `=`, stripping matching surrounding `"` or `'` quotes, and assigning allowlisted variables via `case "$key" in ...` with zero `eval`/`source`). This eliminates arbitrary shell execution and prevents `exit 127` failures on multi-domain `SERVER_NAME` values.

`generate-nginx-conf.sh` then normalizes commas to spaces (`${SERVER_NAME//,/ }`) and resolves `EFFECTIVE_SERVER_NAME` dynamically instead of hardcoding `localhost`:
1. If `SERVER_NAME` is non-empty, use `${SERVER_NAME//,/ }` (space-separated tokens).
2. Else if `CERTBOT_DOMAIN` is non-empty, combine `CERTBOT_DOMAIN` with comma-to-space expanded `CERTBOT_EXTRA_DOMAINS`.
3. Else fall back to `localhost`.

**Validation & Nginx Hash Sizing Rules**:
- **Nginx `server_name` sanitizer (`generate-nginx-conf.sh`)**: Every whitespace-separated token in `EFFECTIVE_SERVER_NAME` MUST match `^[A-Za-z0-9._*-]+$`, MUST NOT begin with `-` or contain `..`, and MUST NOT be a bare single-label non-hostname token (only `localhost`, multi-label hostnames containing `.` with valid DNS labels, or wildcard `*.domain.tld` tokens are accepted; rejecting `;`, `{`, `}`, `$`, quotes, backticks, or control characters). Invalid tokens abort config generation before writing `ptweb.conf`.
- **Nginx `server_names_hash_bucket_size`**: Emit `server_names_hash_bucket_size 128;` inside `nginx.conf` `http {}` (`generate-nginx-conf.sh:123`, right after `types_hash_max_size 2048;`) so long FQDNs or multi-domain `server_name` lists never fail `nginx -t` with `could not build server_names_hash`.
- **ACME FQDN validator (`CertbotManager` in `pt-management`)**: `CERTBOT_DOMAIN` and every entry in `CERTBOT_EXTRA_DOMAINS` MUST pass strict FQDN validation:
  `^(?=.{1,253}$)(?:[a-zA-Z0-9](?:[a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?\.)+[a-zA-Z]{2,63}$`  
  This explicitly rejects `localhost`, IPv4/IPv6 literals, wildcard domains (`*.example.com` cannot use HTTP-01), leading hyphens, consecutive dots, and shell metacharacters. Maximum SAN count is capped at `100` (Let's Encrypt limit).
- **Local Health Check Preservation**: Because `ptweb.conf` defines a single `server` block per port (`80`, `443`, `5000`), Nginx treats it as the implicit `default_server` on each port. Therefore, `curl -k https://localhost/` (`health_check.sh:69-79,222,517`) and `https://localhost:5000/` (`tests/test_tier0_local.sh:66`) continue to route to the active `server` blocks even when `server_name` is set to a production FQDN.

### 2.3 Extensible DNS-01 Considerations

While `CERTBOT_CHALLENGE_TYPE=http-01` is the primary and default mode, `.env` and `CertbotManager` reserve `CERTBOT_CHALLENGE_TYPE` as an allowlisted enum (`http-01` | `dns-01`, defaulting to `http-01`) with strict separation of concerns:
- **When `CERTBOT_CHALLENGE_TYPE=dns-01` is configured in future extensions**:
  - DNS provider plugins (e.g., `certbot-dns-cloudflare`, `certbot-dns-route53`) require API tokens/credentials.
  - **Rule**: DNS-01 credentials MUST NEVER be stored in `.env` (which is readable by `GET /api/env/raw` and `EnvConfigManager` logs). Instead, credentials must live in a dedicated `0600` file under `./certbot/secrets/` (covered by `/certbot/` in `.gitignore`) mounted `:ro` into `pt-certbot` only, and referenced by path (e.g., `--dns-cloudflare-credentials /etc/letsencrypt/secrets/cloudflare.ini`).
  - Until a DNS-01 plugin and credential file are explicitly installed/configured, `CertbotManager` preflight rejects `dns-01` with a clear actionable validation error rather than silently failing inside `certbot`.

## 3. Certificate Issuance, Bootstrap Ordering & Port 443/5000 Coverage

### 3.1 Solving the Bootstrap Deadlock (Before First ACME Issuance)

Nginx fails `nginx -t` and exits immediately if any `ssl_certificate` or `ssl_certificate_key` path referenced in `/etc/nginx/conf.d/ptweb.conf` does not exist on disk. If an operator sets `ENABLE_HTTPS=true` and `TLS_MODE=certbot` before running initial ACME issuance, `/etc/letsencrypt/live/<domain>/fullchain.pem` does not yet exist—meaning `pt-nginx1` would crash-loop and fail to serve port `80` for HTTP-01!

This bootstrap deadlock is eliminated by a **two-layer fallback**:
1. **Host SSL Bootstrap (`deploy.sh` + `generate-ssl-cert.sh`)**:
   - `generate-ssl-cert.sh` is extended with `--if-missing` and `--non-interactive` (plus `NONINTERACTIVE=true` env var support) and enforces `chmod 600 "$KEY_FILE"` and `chmod 644 "$CERT_FILE"`.
   - During `deploy.sh` startup, whenever `ENABLE_HTTPS=true` and either `./ssl/server.crt` or `./ssl/server.key` is absent, `deploy.sh` invokes `bash "${WORKDIR}/generate-ssl-cert.sh" --if-missing` *before* generating Nginx configuration or starting `pt-nginx1`.
2. **Dynamic Path Fallback (`generate-nginx-conf.sh`)**:
   - Update unset/missing-`.env` defaults in `generate-nginx-conf.sh:25-26,35-36` from `/etc/ssl/certs/ssl-cert.pem` and `/etc/ssl/private/ssl-key.pem` to `/etc/ssl/ptweb/server.crt` and `/etc/ssl/ptweb/server.key`.
   - `generate-nginx-conf.sh` resolves `EFFECTIVE_CERT_PATH` and `EFFECTIVE_KEY_PATH` as follows:
     - Normalize legacy `.env` defaults (`/etc/ssl/certs/server.crt` -> `/etc/ssl/ptweb/server.crt`; `/etc/ssl/private/server.key` -> `/etc/ssl/ptweb/server.key`) as well as `/etc/ssl/certs/ssl-cert.pem` / `/etc/ssl/private/ssl-key.pem` (and rely on entrypoint compatibility symlinks in Section 4.2).
     - When `TLS_MODE=certbot` and `CERTBOT_DOMAIN` is non-empty: check on the host/project filesystem (`"$ROOT_DIR/certbot/conf/live/${CERTBOT_DOMAIN}/fullchain.pem"` and `privkey.pem`). If **both** exist and are non-empty, emit:
       - `ssl_certificate /etc/letsencrypt/live/${CERTBOT_DOMAIN}/fullchain.pem;`
       - `ssl_certificate_key /etc/letsencrypt/live/${CERTBOT_DOMAIN}/privkey.pem;`
     - When `TLS_MODE=certbot` and `CERTBOT_DOMAIN` is empty while `SSL_CERT_PATH` or `SSL_KEY_PATH` points under `/etc/letsencrypt/*`: verify the corresponding host files under `"$ROOT_DIR/certbot/conf/"` exist and are non-empty; if missing, fall back cleanly to `/etc/ssl/ptweb/server.crt` and `/etc/ssl/ptweb/server.key`.
     - Otherwise (initial bootstrap prior to first ACME issuance, or `TLS_MODE=self-signed`, or `TLS_MODE=manual`), emit `/etc/ssl/ptweb/server.crt` and `/etc/ssl/ptweb/server.key`.

Because `generate-nginx-conf.sh` runs inside `pt-management` (where `$ROOT_DIR` resolves to `/project` via `SCRIPT_DIR` at `generate-nginx-conf.sh:8-9`) as well as on the host during `deploy.sh`, this host/project check works identically in both execution environments.

### 3.2 Staging, Dry-Run, and Production Issuance Sequence

1. **Pre-Issuance Validation (Preflight in `CertbotManager`)**:
   - Verify `CERTBOT_DOMAIN` (and `CERTBOT_EXTRA_DOMAINS`) pass strict FQDN validation.
   - Verify `CERTBOT_EMAIL` matches strict email syntax (`^[^@\s;'"`$&|<>]+@[^@\s;'"`$&|<>]+\.[^@\s;'"`$&|<>]+$`).
   - Verify `pt-certbot` container is running and `/project/certbot/www` is writable.
   - Ensure `ENABLE_HTTPS` / port `80` ACME carve-out is active in `ptweb.conf` and `pt-nginx1` is running.
2. **Staging / Dry-Run Mode (Recommended First Check)**:
   - `POST /api/certbot/issue` with `{ "staging": true, "dry_run": true }` (or `CERTBOT_STAGING=true`):
     - Executes `docker exec pt-certbot flock -n /etc/letsencrypt/.pt_certbot_op.lock certbot certonly --webroot -w /var/www/certbot --non-interactive --agree-tos --email <email> --cert-name <domain> --expand --keep-until-expiring -d <domain> [-d <san>...] [--staging] [--dry-run]`.
     - **In-Place SAN Expansion (`--cert-name <domain> --expand`)**: Always passing `--cert-name "${CERTBOT_DOMAIN}" --expand` guarantees that adding, removing, or modifying `CERTBOT_EXTRA_DOMAINS` updates `/etc/letsencrypt/live/${CERTBOT_DOMAIN}/` in-place rather than failing in `--non-interactive` mode or creating a mismatched `live/${CERTBOT_DOMAIN}-0001/` lineage.
     - **Dry-run invariant**: When `dry_run=true`, `.env` (`TLS_MODE`, `SSL_CERT_PATH`, `SSL_KEY_PATH`) and `pt-nginx1` configuration are **NOT** modified; full Certbot stdout/stderr is returned to the admin UI.

### 3.3 Unified TLS Coverage Across Port 443 and Port 5000 + `[PROP-C3-03]` Alignment

- **Port `5000` Timeout Alignment (`CertbotManager` < Gunicorn < Nginx)**: Currently `generate-nginx-conf.sh:475-476` (HTTPS `:5000`) and `lines 506-507` (HTTP `:5000`) set `proxy_send_timeout 90; proxy_read_timeout 90;`, which is shorter than Gunicorn's `--timeout 120` (`pt-management/entrypoint.sh:56,65`). #### `[PROP-C3-03]` & `[PROP-C3-05]` Hardening Alignment (with Necessary Corrections)
Applying `docs/proposals/02_improvement_proposals.md:1300-1417` requires two critical safeguards for Certbot + self-signed coexistence:
1. **ECDSA + RSA Mozilla Intermediate Ciphers (`generate-nginx-conf.sh:409-411,451-453`)**:  
   Certbot 2.x issues **ECDSA P-256** keys by default, while `generate-ssl-cert.sh:39` generates **RSA 2048** keys. Both port `443` and port `5000` MUST replace `HIGH:!aNULL:!MD5` + `ssl_prefer_server_ciphers on` with Mozilla Intermediate AEAD ciphers supporting both ECDSA and RSA:
   ```nginx
   ssl_protocols TLSv1.2 TLSv1.3;
   ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305:DHE-RSA-AES128-GCM-SHA256:DHE-RSA-AES256-GCM-SHA384;
   ssl_prefer_server_ciphers off;
   ssl_session_cache shared:SSL:10m;
   ssl_session_timeout 1d;
   ssl_session_tickets off;
   ```
   *(Note: `ssl_session_cache shared:SSL:10m;` is safe across both `:443` and `:5000` server blocks as long as both reference the exact same cache name and size `SSL:10m`, or is defined once in `nginx.conf` `http {}`.)*
2. **Conditional HSTS (Only When Active Let's Encrypt Cert Is Served)**:  
   Emitting `Strict-Transport-Security "max-age=63072000; includeSubDomains; preload" always;` (`02_improvement_proposals.md:1327`) when `TLS_MODE=self-signed` pins browsers to HTTPS on `localhost` for 2 years with no bypass if HTTPS is later disabled or tested locally. Therefore, `generate-nginx-conf.sh` emits `add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;` **only** when `TLS_MODE=certbot` and `USING_CERTBOT_CERT=true` (an active Let's Encrypt certificate exists on disk, including staging certificates so staging validation verifies HSTS end-to-end), and omits HSTS completely on `self-signed`, `manual`, and bootstrap fallback modes.
3. **Avoid `ssl_stapling on`**:  
   Do **NOT** emit `ssl_stapling on; ssl_stapling_verify on;` (`02_improvement_proposals.md:1333-1334`). Self-signed certificates have no OCSP responder (producing noisy Nginx startup warnings), and Let's Encrypt ended OCSP responder service in 2025 in favor of CRLs / short-lived certificates.

## 4. Automated Renewal & Zero-Downtime `pt-nginx1` Reload

### 4.1 `pt-certbot` Container Service (`ptweb-vnc/pt-certbot/`)

A dedicated lightweight container service `pt-certbot` encapsulates the ACME client without bloating `pt-management` or `pt-nginx1`:
- **`ptweb-vnc/pt-certbot/Dockerfile`**:
  ```dockerfile
  FROM certbot/certbot:latest
  COPY entrypoint.sh /entrypoint.sh
  RUN chmod +x /entrypoint.sh
  ENTRYPOINT ["/entrypoint.sh"]
  ```
- **Privilege & Isolation Posture**:
  - Runs as `root` (required so Certbot can write `0600` private keys into `/etc/letsencrypt/archive/`).
  - **NO `/var/run/docker.sock` mount** (least privilege: `pt-certbot` cannot manipulate sibling containers or host Docker daemon).
  - Connected to `ptnet` (and `pt-stack` if present) **without** `--dns=127.0.0.1` so it can reach external ACME CA endpoints over outbound TCP `443`.
- **Volume Mounts**:
  - `./certbot/conf:/etc/letsencrypt:rw`
  - `./certbot/www:/var/www/certbot:rw`
- **`ptweb-vnc/pt-certbot/entrypoint.sh` (12-Hour Automated Renewal Loop, POSIX `/bin/sh`)**:
  - **Immediate `SIGTERM`/`SIGINT` Shutdown**: In Alpine BusyBox `/bin/sh`, a foreground `sleep 43200` blocks signal trap execution until sleep exits (causing `docker stop pt-certbot` to hang `10s` until `SIGKILL`). Therefore, `entrypoint.sh` MUST sleep asynchronously and clean up the child process in its trap:
    ```sh
    SLEEP_PID=""
    cleanup() {
      [ -n "$SLEEP_PID" ] && kill "$SLEEP_PID" 2>/dev/null || true
      exit 0
    }
    trap cleanup TERM INT
    # inside loop:
    sleep "$INTERVAL" &
    SLEEP_PID=$!
    wait "$SLEEP_PID" || true
    SLEEP_PID=""
    ```
  - **Safe `.env` Reading (Never `source` or `.`)**: `certbot/certbot:latest` runs Alpine `/bin/sh` (which lacks bash `source`), and `. /app/.env` would fail on space-separated or quoted variables. `entrypoint.sh` MUST NEVER `source` or `.` `/app/.env`. Instead, every `CERTBOT_RENEW_INTERVAL` (`43200`s default) cycle reads `CERTBOT_AUTO_RENEW` from `/app/.env` (if present) using a safe POSIX `while IFS= read -r` key-value parser that strips matching surrounding `"` / `'` quotes without executing shell words (falling back to container env `${CERTBOT_AUTO_RENEW:-true}`), allowing UI toggles of `CERTBOT_AUTO_RENEW` to take effect on the next cycle without recreating `pt-certbot`.
  - Checks:
    1. `CERTBOT_AUTO_RENEW=true`.
    2. At least one renewal config exists in `/etc/letsencrypt/renewal/*.conf`.
  - Executes renewal under an `flock` lock (`/etc/letsencrypt/.pt_certbot_op.lock`) to serialize against on-demand `docker exec pt-certbot certbot ...` invocations from `pt-management`:
    ```sh
    flock -n /etc/letsencrypt/.pt_certbot_op.lock \
      certbot renew --webroot -w /var/www/certbot --non-interactive \
      --deploy-hook 'date -u +%s > /etc/letsencrypt/.nginx-reload-requested'
    ```
  - Note: `--deploy-hook` runs **only** when Certbot actually renews a certificate (typically when `< 30` days remain), not on no-op 12-hour checks. The trigger file `.nginx-reload-requested` is placed inside `/etc/letsencrypt/` (never inside `/var/www/certbot`, keeping the public HTTP-01 webroot clean). Also, `pt-certbot` ensures `/var/www/certbot/.well-known/acme-challenge` exists on its `:rw` mount on startup.

### 4.2 Directory Mounts Replacing Single-File `:ro` Bind Mounts

Single-file bind mounts (`./ssl/server.crt:/etc/ssl/certs/server.crt:ro`) bind Nginx and `pt-management` to a specific filesystem inode. Replacing or rotating a file via `mv` or symlink re-pointing in `live/<domain>/` leaves containers reading the stale old inode until the container is recreated.

All deployment scripts and Compose definitions MUST migrate to **directory-level bind mounts**:

| Host Path | `pt-nginx1` | `pt-certbot` | `pt-management` | Purpose |
|---|---|---|---|---|
| `./ssl` | `/etc/ssl/ptweb:ro` | *(not mounted)* | `/project/ssl:rw` (via `/project`) | Self-signed & manually uploaded certs/keys + `.backups/` |
| `./certbot/conf` | `/etc/letsencrypt:ro` | `/etc/letsencrypt:rw` | `/etc/letsencrypt:rw` (and `/project/certbot/conf`) | ACME account, `live/`, `archive/`, `renewal/`, reload trigger |
| `./certbot/www` | `/var/www/certbot:ro` | `/var/www/certbot:rw` | `/var/www/certbot:rw` | ACME HTTP-01 webroot (`/.well-known/acme-challenge/`) |

**Critical System Directory Constraint**: Do **NOT** directory-mount `./ssl` onto `/etc/ssl/certs`. On Debian Bookworm (`ptweb-vnc/pt-nginx/Dockerfile:43,49`), `/etc/ssl/certs/ca-certificates.crt` lives in `/etc/ssl/certs`; a bind mount there would shadow the system CA bundle. Instead, mount `./ssl` at `/etc/ssl/ptweb:ro` and create compatibility symlinks inside `pt-nginx/docker-entrypoint.sh`:
```sh
ln -sfn /etc/ssl/ptweb/server.crt /etc/ssl/certs/server.crt
ln -sfn /etc/ssl/ptweb/server.key /etc/ssl/private/server.key
```
This preserves backward compatibility for any existing `.env` containing `SSL_CERT_PATH=/etc/ssl/certs/server.crt` while resolving through `/etc/ssl/ptweb` on disk without stale bind-mount inodes.

### 4.3 Dual Zero-Downtime Reload Mechanism (`pt-nginx1`)

To support both autonomous 12h renewals (`pt-certbot`, which has **no** Docker socket) and immediate admin-UI feedback (`pt-management`), `pt-nginx1` uses a **dual reload mechanism**:

#### Mechanism A: Read-Only Entrypoint Content-Hash Watcher (`ptweb-vnc/pt-nginx/docker-entrypoint.sh`)
`ptweb-vnc/pt-nginx/Dockerfile` is updated to install `docker-entrypoint.sh` as `ENTRYPOINT ["/docker-entrypoint.sh"]` while keeping `CMD ["nginx", "-g", "daemon off;"]`.
At container start, `docker-entrypoint.sh`:
1. Creates **only** container-writable directories `mkdir -p /etc/ssl/certs /etc/ssl/private` (MUST **NOT** run `mkdir -p /etc/ssl/ptweb` or `mkdir -p /var/www/certbot/.well-known/acme-challenge`, because `/etc/ssl/ptweb` and `/var/www/certbot` are `:ro` bind mounts in `pt-nginx1` and `mkdir -p` on a `:ro` mount fails under `set -e` with `Read-only file system`; host directories `./ssl`, `./certbot/conf`, and `./certbot/www/.well-known/acme-challenge` are created on the host by `deploy.sh`/`deploy-full.sh` and via `:rw` mounts in `pt-certbot`/`pt-management`). Creates the `/etc/ssl/{certs,private}/server.{crt,key}` compatibility symlinks (`ln -sfn /etc/ssl/ptweb/server.crt /etc/ssl/certs/server.crt` and `ln -sfn /etc/ssl/ptweb/server.key /etc/ssl/private/server.key`).
2. Runs `nginx -t` on boot to fail fast on broken static configuration.
3. Spawns a lightweight background subshell watcher (`NGINX_CERT_WATCH_INTERVAL=${NGINX_CERT_WATCH_INTERVAL:-15}`) using tools already verified present in `pt-nginx1` (`/usr/bin/sha256sum`, `/usr/bin/stat`, `/usr/bin/sleep`):
   - Computes a composite fingerprint over:
     - `/etc/nginx/nginx.conf` (catches GeoIP map and `http {}` updates)
     - `/etc/nginx/conf.d/ptweb.conf`
     - `readlink -f` targets of the active `ssl_certificate` and `ssl_certificate_key` parsed from `ptweb.conf` (so Certbot symlink updates `live/<domain>/fullchain.pem -> ../../archive/<domain>/fullchain2.pem` are detected immediately, not missed by symlink `mtime`)
     - `/etc/ssl/ptweb/server.crt` and `/etc/ssl/ptweb/server.key`
     - `/etc/letsencrypt/.nginx-reload-requested` (content/mtime)
   - Whenever the fingerprint changes:
     1. Sleeps `2s` (debounce window so atomic cert + key pair writes complete together before testing).
     2. Re-computes fingerprint; runs `nginx -t`.
     3. If `nginx -t` exits `0`, runs `nginx -s reload` (sending `SIGHUP` to PID 1).
     4. If `nginx -t` fails, logs a warning and leaves existing workers running untouched (zero outage).
4. Executes `exec "$@"` so **`nginx` master remains PID 1 (`root`)**, preserving clean `SIGTERM`/`SIGQUIT` signal handling and worker privilege drop (`user nginx;` in `nginx.conf:2`).

#### Mechanism B: Synchronous Reload from `pt-management`
When an admin clicks **Issue**, **Renew**, **Switch Mode**, **Upload Certificate/Key**, or **Apply Configuration** in `pt-management`, `EnvConfigManager.reload_nginx()` runs synchronously via the mounted Docker socket:
```python
docker exec pt-nginx1 nginx -t
docker exec pt-nginx1 nginx -s reload
```
This gives the admin API immediate pass/fail feedback without waiting up to `15s` for the polling loop. If `nginx -t` fails, `reload_nginx()` returns `(False, stderr)` immediately and does **not** restart `pt-nginx1` (fixing the crash-loop hazard in `env_config.py:365-369`).

#### WebSocket Tunnel Preservation
Verified in `ptweb-vnc/pt-nginx/conf/ptweb.conf:135-149` and `nginx.conf:57-60`:
- `nginx -s reload` instructs the `root` master process (`PID 1`) to parse the updated configuration, read the new `0600` certificate/key files from `/etc/ssl/ptweb` or `/etc/letsencrypt`, spawn new `nginx` worker processes for incoming TLS handshakes, and send `SIGQUIT` (graceful shutdown) to old workers.
- Because `worker_shutdown_timeout` is unset in `nginx.conf`, old workers continue serving existing `/guacamole/websocket-tunnel` connections until students close their sessions naturally—achieving true zero-downtime certificate rotation.

### 4.4 Lock & Concurrency Control
Two independent processes can invoke `certbot` concurrently:
1. `pt-certbot`'s 12h background renewal loop.
2. `pt-management` (which itself runs `gunicorn --workers 2` per `pt-management/entrypoint.sh:55,64`) handling concurrent HTTP requests to `/api/certbot/issue` or `/api/certbot/renew`.

Concurrency is guarded at two levels:
- **Python Worker Lock (`pt-management`)**: `CertbotManager` acquires a non-blocking exclusive `fcntl.flock(fd, LOCK_EX | LOCK_NB)` on `/tmp/pt_certbot.lock` before any `issue`, `renew`, or `switch-mode` execution. A second concurrent request immediately receives HTTP `409 Conflict` (`"Another certificate operation is currently in progress"`).
- **Container / Certbot Lock (`pt-certbot`)**: `pt-certbot/entrypoint.sh` and `pt-management`'s `docker exec pt-certbot` command wrap `certbot` in `flock -n /etc/letsencrypt/.pt_certbot_op.lock ...` (in addition to Certbot's native `/etc/letsencrypt/.certbot.lock`). If the background 12h loop is actively renewing when the admin clicks **Issue/Renew**, `pt-management` detects exit code `1` from `flock` (or Certbot's lock message) and returns a clean `409 Conflict` / retryable status instead of hanging or corrupting state.

## 7. Coexistence, Security & Key Handling

### 7.1 `TLS_MODE` State Machine & Coexistence

Three TLS modes coexist cleanly under `TLS_MODE` (`self-signed` | `manual` | `certbot`):

```
                    ┌───────────────────────────────────┐
                    │       self-signed (default)       │
                    │  generate-ssl-cert.sh -> ./ssl/   │
                    │  Nginx: /etc/ssl/ptweb/server.*   │
                    └───────┬───────────────────▲───────┘
                            │                   │
       Upload matched pair  │                   │ switch-mode('self-signed') /
       (FileUploadManager)  │                   │ generate-ssl-cert.sh
                            ▼                   │
                    ┌───────────────────┐       │
                    │      manual       │───────┘
                    │ /project/ssl/*    │
                    │ Nginx: ptweb/*    │
                    └───────┬───────────┘
                            │                   ▲
   issue() succeeds         │                   │ switch-mode('manual')
   (CertbotManager)         ▼                   │ (if /project/ssl/* valid pair)
                    ┌───────────────────┐       │
                    │      certbot      │───────┘
                    │ /etc/letsencrypt/ │
                    │ live/<domain>/*   │
                    └───────────────────┘
```

- **`self-signed` <-> `manual` Boundary**: Both store files under `./ssl/server.{crt,key}` (`/etc/ssl/ptweb/server.{crt,key}` in `pt-nginx1`). When switching from `manual` back to `self-signed` via UI or script, existing backups in `/project/ssl/.backups/` allow instant restoration of prior certs, or `generate-ssl-cert.sh` regenerates a fresh `localhost` self-signed pair.
- **Non-Destructive Switching**: Switching `TLS_MODE=certbot` leaves `./ssl/server.{crt,key}` intact as fallback; switching `TLS_MODE=manual` or `self-signed` leaves `/etc/letsencrypt/live/<domain>/` intact so switching back does not require re-issuing from Let's Encrypt.

### 7.2 `generate-ssl-cert.sh` & `FileUploadManager` Hardening

1. **`generate-ssl-cert.sh` (`lines 1-68`)**:

2. **`FileUploadManager` (`pt-management/ptmanagement/api/file_upload.py`) & `upload_routes.py`**:
   - **Writable Host Storage**: Resolve `project_root = os.environ.get('PROJECT_ROOT', '/project')` (overridable via `SSL_DIR` / `SSL_KEY_DIR` or constructor args for isolated unit tests). Because `/project` is mounted RW (`deploy-full.sh:116`, `docker-compose.yml:79`) and `/ssl/*` is in `.gitignore:16`, backups persist across container recreations and never trigger `EROFS`.
   - **Extension Fix**: Allow `'server.key': ['key', 'pem']` (`file_upload.py:19`), aligning with `env_settings.html:636` (`accept=".key,.pem"`).

     - Validate uploaded `server.crt` in `FileUploadManager.validate_file_content()` by explicitly rejecting any combined-PEM `PRIVATE KEY` block (`-----\s*(?:BEGIN|END)\b[^-\r\n]*PRIVATE\s+KEY[^-\r\n]*-----`) before running `['openssl', 'x509', '-in', tmp_path, '-noout', '-subject', '-issuer', '-dates', '-ext', 'subjectAltName']` via a `0o600` temp file.
     - Validate uploaded `server.key` via temp file (`0o600`) with `['openssl', 'pkey', '-in', tmp_path, '-pubout', '-passin', 'pass:']`. Passing `-passin pass:` deterministically rejects passphrase-protected keys (which would stall/fail Nginx reload) while validating RSA, ECDSA, and Ed25519 keys.
     - Implement `verify_cert_key_pair(cert_path, key_path)` comparing `openssl x509 -in <cert> -pubkey -noout` stdout against `openssl pkey -in <key> -pubout -passin pass:` stdout.
   - **Safe Staged Upload & Activation (`/project/ssl/.pending/` Staging — Never Overwrite Active Files With an Unpaired Half)**:
     - Because the UI uploads `server.crt` and `server.key` via two separate buttons (`POST /api/upload/certificate`, `POST /api/upload/key`), writing an uploaded half directly into `/project/ssl/server.{crt,key}` while the counterpart is still from an older pair would leave `/etc/ssl/ptweb/` mismatched on disk—causing `pt-nginx1`'s 15s watcher to fail `nginx -t` and **crash-looping `pt-nginx1` on any container restart** (locking out `:443` and `:5000`).
     - **Rule**:
       1. Never overwrite active `/project/ssl/server.crt` or `/project/ssl/server.key` with an unpaired half.
       2. After validating the uploaded file in a `0o600` temp file (`openssl x509` or `openssl pkey -passin pass:`), write it into `/project/ssl/.pending/` (`0o700` directory; `0o644` for `.pending/server.crt`, `0o600` for `.pending/server.key`).
       3. Run `verify_cert_key_pair()` against the staged counterpart in `/project/ssl/.pending/` (if present) **or** against the active counterpart in `/project/ssl/`.
       4. If `verify_cert_key_pair()` returns `False`: leave active `/project/ssl/server.{crt,key}` and `pt-nginx1` completely untouched and return `{'success': True, 'staged': True, 'pair_matched': False, 'reloaded': False, 'warning': 'File staged in .pending/; upload matching counterpart to activate'}`.
       5. Only when `verify_cert_key_pair()` returns `True`: back up the existing active file(s) being replaced to `/project/ssl/.backups/`, atomically promote the matched file(s) from `/project/ssl/.pending/` into `/project/ssl/server.{crt,key}` (`0o644` cert, `0o600` key) and remove the promoted `.pending/` files, set `TLS_MODE=manual`, `SSL_CERT_PATH=/etc/ssl/ptweb/server.crt`, `SSL_KEY_PATH=/etc/ssl/ptweb/server.key`, regenerate `ptweb.conf`, run `nginx -t`, and reload `pt-nginx1`.
   - **Access Control, Path Validation & `POST /api/upload/restore` (`upload_routes.py:180`, `file_upload.py:249-359`)**:
     - Enforce `@require_admin` on **all** `upload_routes.py` endpoints (including `GET /info/*`, `GET /backups*`, `POST /certificate`, `POST /key`, `POST /restore`, and `POST /backup/delete`).
     - Replace the `startswith()` backup path check (`file_upload.py:265,346`) with `resolved = Path(backup_path).resolve(); resolved.relative_to(Path(self.backup_dir).resolve())` **AND** `resolved.is_file()` (ensuring directory paths such as `backup_dir` itself cannot pass validation).

### 7.3 Private Key Safety, `.gitignore`, Secret Redaction & Single-File Invariants

- **Private Key Privilege Separation**: `pt-certbot` writes Let's Encrypt private keys (`archive/<domain>/privkeyN.pem`) with mode `0600` (`root:root`). `pt-nginx1` master process executes as `root` (`PID 1`), reads the `0600` private key into memory during startup and `nginx -s reload` via `:ro` directory mount, and then serves client traffic from unprivileged `user nginx;` (`nginx.conf:2`) worker processes. Host `./ssl/server.key` is likewise hardened to `0600`.
- **`.gitignore` Protection**: Add `/certbot/` to `.gitignore` (alongside existing `/ssl/*` at `.gitignore:16` and `*.env` at `.gitignore:17`) so ACME private keys, account registration keys, and any future DNS-01 secret files can never be committed to Git.
- **Secret Redaction**: `CERTBOT_EMAIL` is non-secret ACME metadata. However, if future extensions add any token/secret variable (e.g. DNS-01 credentials path or `PTADMIN_PASSWORD`), `EnvConfigManager._sanitize_for_logging()` (`env_config.py:556-565`) should redact keys containing `secret`, `token`, `password`, or `key` in addition to `path`.
- **`nginx.conf` Single-File Mount Invariant**: `deploy.sh:352` and `docker-compose.yml:55` bind-mount `ptweb-vnc/pt-nginx/nginx.conf` as a single file. Because `generate-nginx-conf.sh:211` writes via shell redirection `> "$OUT_NGINX_CONF"` (truncating and writing in-place, preserving the inode), updates propagate into `pt-nginx1` without container recreation. M2/M3 MUST preserve this in-place truncation pattern (never replacing `nginx.conf` with `mv` / atomic rename).
